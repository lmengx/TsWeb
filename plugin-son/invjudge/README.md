# InvJudge —— 玩家背包判定插件（合成合法性校验）

> **版本**：1.0.0  
> **作者**：lmx12330  
> **状态**：第一期（仅记录模式，不拦截不处罚）

## 功能概述

通过反编译泰拉瑞亚客户端/服务端源码（本地 `scripts/反编译/参考源码/`），确认了多人模式下**合成为客户端权威**的关键事实：

- Terraria 多人模式**没有专门的合成包**（MessageID 全表核对，`123` 是武器架而非合成）；
- 客户端在本地执行 `Main.CraftItem(recipe)` → `Recipe.Create()`：从背包扣材料（不发包）、从打开的箱子扣材料（发 **32 SyncChestItem**）、产物进鼠标物品（发 **5 SyncEquipment**）；
- 客户端通过 `Main.TrySyncingMyPlayer()`（`Main.cs:17415`）定期对比本地背包与上次同步快照，**任何槽位变化（含合成扣材、产物）都会自动发 packet 5 同步给服务端**。

因此服务端**永远看不到"合成"本身**，只能从 **packet 5（背包/银行/时装槽）** 与 **packet 32（箱子槽）** 的变化流中反推合成操作并校验数学。

### 检测目标

1. **合成比例合法性（核心）**：把每个玩家的槽位变化流按时间窗口聚合，反推可能的合成操作，校验 **扣材可支撑的合成次数 vs 实际产物次数**：
   - 正常：扣 10 材料 → 产 10 产物（倍率 1.0）
   - 异常：扣 1 材料 → 产 2 产物（倍率 2.0）→ **手机端 1 材料做 2 物品 bug 的特征**
2. **微光可分解配方重点监控**：产物可被微光还原分解（`ShimmerTransforms.GetDecraftingRecipeIndex >= 0`）的配方开启**严格模式**——任何产量超出扣材支撑量即记录（这是「1 材料做 2 物品 + 微光分解 = 无限刷」漏洞链的源头环节）。
3. **仅产出无消耗提示**：窗口内只出现产物、没有任何扣材，且产物为微光可分解物品时记录提示（微光分解链的早期信号）。

## 安装

1. 构建：`dotnet build InvJudge.csproj -c Release`
2. 将 `bin/Release/net9.0/InvJudge.dll` 复制到服务器 `ServerPlugins/` 目录
3. 重启服务器

## 配置

配置文件：`tshock/InvJudge/config.json`（首次启动自动生成）

```json
{
  "启用": true,
  "检测窗口毫秒": 1500,
  "微光可分解严格模式": true,
  "普通合成产量容差": 1.05,
  "日志目录": "InvJudge",
  "记录通过日志": false
}
```

| 字段 | 类型 | 默认 | 说明 |
|------|------|------|------|
| `启用` | bool | true | 总开关 |
| `检测窗口毫秒` | int | 1500 | 槽位变化聚合窗口；窗口空闲超过该时长即触发检测 |
| `微光可分解严格模式` | bool | true | 产物为可微光分解物品时，产量必须精确等于扣材支撑量 |
| `普通合成产量容差` | double | 1.05 | 普通配方允许的产量倍率容差（1.0=精确，1.05=允许 5% 溢出防误报） |
| `日志目录` | string | InvJudge | 日志输出目录（相对 tshock/） |
| `记录通过日志` | bool | false | 是否记录合法合成（调试用） |

**violations.log**（违规）：

```
[2026-09-15 10:00:00] 玩家=Steve(acc:3) 窗口=5次变化 合成比例异常: 扣材1x 木材 / 产量2x 木剑 | 配方[123] [123] 木剑 = 1x木材 + 1x铁锭 (产物1)[微光可分解]: 扣材可支撑 1 次, 实际产出 2 次 (倍率 2.00, 微光可分解严格模式)
```

**passes.log**（合法合成，需开启 `记录通过日志`）：

```
[2026-09-15 10:00:05] 玩家=Steve(acc:3) 合法合成: 木剑 x1 (扣材1x 木材, 配方[120])
```

## 检测原理

### 窗口聚合

每个玩家的槽位变化（packet 5 / 32）被聚合进一个时间窗口：

- 窗口首次变化时记录起始时间；
- 每次变化刷新最后变化时间；
- 服务端 tick 每 30 tick（0.5s）检查：窗口空闲超过 `检测窗口毫秒` → 触发检测并清空窗口。

窗口内按**物品类型**累计净变化：负值=消耗（材料），正值=产出（产物）。纯槽位移动（A 槽 -5、B 槽 +5 同物品）净变化为 0，不会误判。

### 配方匹配

`RecipeIndex.MatchCraft(consumed, produced)`：

1. 对每个产出的物品类型，查找 `Main.recipe` 中能产出它的配方；
2. 校验消耗集合是否满足配方的全部需求（含 RecipeGroup 组需求，如 anyWood）；
3. 计算 `craftByConsumed = min(consumed[req] / req.stack)`（扣材可支撑次数）；
4. 计算 `craftByProduced = produced[result] / createItem.stack`（实际产出次数）；
5. 倍率 = `craftByProduced / craftByConsumed`：
   - 微光严格模式（产物可微光分解）：倍率 > 1.0 → 违规
   - 普通配方：倍率 > 容差（默认 1.05）→ 违规

### 进服同步保护

客户端登录时会批量发送全部槽位包（进服同步风暴）。插件在 TShock 的 `HasSentInventory` 置位前只把槽位值写入账本基线，不聚合 delta，避免把「客户端声明背包 = 服务端初始状态」误判为操作。

## 与现有反作弊的关系

TSWeb 主插件的 `AntiCheat` / `ItemDetection` 是**扫描式**检测（按进度限制物品，定时/手动扫描背包）；本插件是**事件式**检测（在槽位变化发生时实时校验操作合法性），二者互补。
